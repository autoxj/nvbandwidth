二、MultinodeDeviceToDeviceTransfer 精读（1 对 1 读写）

2.1 函数功能总结

一句话职责：对 worldSize 个 rank 的每一对有序组合 (first, second)，测量"以 first 所在 GPU 为发起者、second 为对端"的跨节点拷贝带宽——Write 测 first 的推出带宽（PREFER_SRC），Read 测 first 的拉入带宽（PREFER_DST），最终填出一张 worldSize × worldSize 的带宽矩阵。

  • 谁在跑：4 个 rank 执行完全相同的 run() 代码，没有角色分支——分工由 dispatchMemcpy 的"标注-认领"结果自然产生（执行者满清单，旁观者空清单）。
  • 数据从哪来：pair 列表由 rank0 生成后广播（generateTestPairs 静态缓存，仅首次计算）。
  • 内存从哪来：每对临时构造两个 Unicast 缓冲，owner 创建物理显存、全员通过 fabric 句柄映射，用完即析构。
  • MPI 用在哪：只用于"对齐"和"传话"（Barrier / Bcast / Iprobe 心跳）；数据搬运本身全程走 GPU（SM/CE/TMA + NVLink），毫秒级起跑对齐靠共享显存闸门而非网络。
  • 每对 MPI 账目：3 次 Bcast（src 构造 + dst 构造 + 结果广播）+ 10 次 Barrier（构造 2 + 采样 3×2 + 析构 2，另有一次列表生成期的 Barrier）。

2.4 generateTestPairs 流程图

函数职责：为整次运行生成"测哪些 pair"的有序列表。三种产出模式：全量（targetNumPairs = -1 或恰好等于全对数，返回 W×(W-1) 全部有序对；超过全对数的取值在启动校验时直接报错）与抽样（目标数小于全对数，两遍挑选：先保证每张卡至少出现一次，再随机补足）。结果存函数级 static 缓存，所有测试用例共享同一份（所以只在第一次调用时真正计算）。全程只有 rank0 计算，其余 rank 只在 Barrier 等待并接收广播。

targetNumPairs 从哪来、默认是多少：来自命令行 -P / --targetNumPairs N，不设置时默认 -1（即测全部 pair）（定义于 test_settings.h 的 kDefaultTargetPairs）。取值含义：

  • -1（默认）：视为全对数 W×(W-1)，全量测试，不做抽样
  • 0：直接返回空列表（不测任何 pair）
  • 1 ~ 全对数-1：进入抽样模式，只测 N 对
  • <-1 或 >全对数：启动时参数校验直接报错退出（nvbandwidth.cpp）

两个静态缓存列表的含义：

  • allValidPairs（全量表）：worldSize × (worldSize-1) 个有序对 (src, dst)（src ≠ dst），即"测试的完整宇宙"；生成后用固定种子 0xBAADF00D 洗牌，只影响执行顺序、不影响覆盖面。非抽样模式下它就是最终测试列表。
  • selectedPairs（抽样表）：当目标对数 < 全对数时，从全量表中挑出的子集；两遍挑选保证小样本下每张 GPU 仍至少出现在一个 pair 里。抽样模式下它才是最终测试列表。全量模式下它保持为空、不被使用。

返回值示例（worldSize = 4，默认全量模式）：全量表共 4 × 3 = 12 个有序对，洗牌后的执行顺序形如（顺序为示意，实际由固定种子 0xBAADF00D 决定）：

  • (0,2) → (3,1) → (1,3) → (2,0) → (0,3) → (3,2) → (1,0) → (2,3) → (3,0) → (0,1) → (2,1) → (1,2)
  • 第一对 (0,2) 即 2.3 流程图贯穿使用的例子：srcNode owner = rank0、peerNode owner = rank2（成员逐 rank 对比见 2.5），执行者为 rank0；这一对完整跑完（构造 → 采样 → 写矩阵 → 析构）后才进入下一对 (3,1)，直到 12 对全部完成
  • 抽样模式示例（-P 4）：只返回 4 对，形如 {(0,2), (1,3), (3,0), (2,1)}——两遍挑选保证 0/1/2/3 每张卡都至少出现一次

关键行（multinode_memcpy.cpp L328）：Barrier 之后所有 rank（不只是 rank0）都要置位 pairsCalculated。若漏掉：第二次调用时 rank0 在缓存检查处提前返回，而非 rank0 会落到 Barrier 死等——两侧分支不对称，直接死锁。

构造执行完后，到底发生了什么？

  • 物理显存只有两块：rank0 在节点 A 卡 0 上 cuMemCreate 一块（srcNode，512MB 向上取整对齐），rank2 在节点 B 卡 0 上 cuMemCreate 另一块（peerNode）。
  • 跨进程传递的是 fabric 句柄 fh：Bcast 的载荷是 64 字节的 CUmemFabricHandle。其他 rank 拿 fh cuMemImportFromShareableHandle 换出自己的 handle 后，各自 cuMemAddressReserve 一个本地 VA，把同一块物理显存 cuMemMap 进自己的虚拟地址空间，再用 cuMemSetAccess 给自己的 GPU 发 READWRITE 授权。
  • 每个 rank 映射出的是自己的地址：4 个进程对同一块物理显存各持一个不同的本地 VA（见表 4/表 5）——CUDA 不允许两个进程共用同一个虚拟地址值，共享的载体是物理页，不是 VA。

2.6 doMemcpy：派发之后怎么执行

调用链：run() 中的 memcpyInstance.doMemcpy(peerNode, srcNode)（multinode_testcases.cpp L64，READ 方向时两个实参对调）→ 单 buffer 重载把两个 buffer 包成单元素 vector（memcpy.cpp L352-356）→ vector 版做两件事：dispatchMemcpy 派发（2.3 的⑥）+ doMemcpyCore 执行采样，最后返回 result[0]（L434-438）。

  • 一句话职责：在派发结果之上完成"采样 × 3 轮，每轮入队闸门 + warmup + 正式拷贝 × loopCount → 放行 → 校验 → event 算带宽"的完整测量，返回本用例口径（FIRST/SUM/TOTAL/VECTOR）的最终带宽数值。
  • 谁在干活：4 个 rank 执行同一份 doMemcpyCore 代码，靠 info.srcBuffers.size() 分活——执行者 rank0 清单长度 1，所有 for 循环进 1 次；空闲 rank1/2/3 长度 0，循环体 0 次进入，但 totalEnd 照建、Barrier 与闸门义务照履行。
  • 两级循环：外层 averageLoopCount（默认 3）轮采样（跨轮统计均值与稳定性），内层 loopCount（默认 16）次拷贝（单轮测量内反复搬运）。
  • 起跑对齐：先把 spin 闸门 kernel 和拷贝全部入队（流被闸门卡住不动），再由 host 一次性 release——所有 GPU 同一瞬间开跑，消除 host 逐条入队的抖动。
  • 计时方式：CUDA event 对（startEvents[i] / endEvents[i]），带宽 = adjustedCopySize × loopCount ÷ 耗时；SM 拷贝可能截断尺寸，所以用 getAdjustedCopySize 返回的实际值。

2.7 dispatchMemcpy：零通信的任务分活

函数职责（multinode_memcpy.cpp L383-416）：输入全量任务清单（srcNodesUnfiltered / dstNodesUnfiltered，所有 rank 持有完全相同的一份）和上下文偏好，输出 MemcpyDispatchInfo——不发生任何 MPI 通信，4 个 rank 靠相同输入 + 相同代码各自独立推出一致的派发结论。

  • 三步机制：① 标注——给每个任务写上"该谁执行"（执行者的 MPI_rank + 其 CUDA context）；② 认领——标注值等于自己 worldRank 的任务才收进活清单；③ 记 master——取未过滤表首元素作为 rankOfFirstMemcpy（闸门 master 与结果 Bcast root）。
  • 标注规则：PREFER_SRC 且 src 有 ctx → 执行者 = src 的 owner；否则 dst 有 ctx → 执行者 = dst 的 owner。多节点路径的 getPrimaryCtx() 恒非空（Unicast/Local/Multicast 都走 cuDevicePrimaryCtxRetain），分支实际只由 ctxPreference 决定。
  • 过滤即身份：执行者收到满清单、空闲 rank 收到空清单——活清单的长度就是"我干不干活"的全部依据，下游 for 循环按长度自然分活，无需任何标志位。
  • -1 哨兵：ranksUnfiltered 初始化为 -1，标注不到执行者的任务（host buffer 等无 ctx 场景）在认领阶段被自动丢弃——多节点 D2D 路径不会出现。
  • 通用性：1 对 1 = 1 个任务；多打一 / 一打多 = W-1 个任务（各 rank 各认领 1 个）；多打多 = 每 rank 认领多个——机制不变，只是清单更长。

2.8 NodeHelper：单节点与多节点的分岔点

定位（memcpy.h L116-139）：NodeHelper 是"执行期跨进程协同"的策略接口——11 个纯虚函数分四组：派发（dispatchMemcpy）、结果归集（calculateTotal/Sum/First/VectorBandwidth）、同步（synchronizeProcess / barrierAllRanks / streamSynchronizeWrapper）、闸门（streamBlocker 三件套）。另有静态函数 selectExecutingBuffer（非虚函数，供单节点实现复用）。doMemcpyCore 是单/多节点共用的模板代码，不能直接写 MPI——同一个函数要同时服务单进程（无 MPI 环境，直接调 MPI 会崩）和多进程（需要协同），差异全部下沉到这个接口。

  • 选择点在用例侧：单节点用例构造 MemcpyOperation 时固定 new NodeHelperSingle()（memcpy.cpp L340）；多节点用例传入 NodeHelperMulti（multinode_testcases.cpp）。两者在编译期由 MULTINODE 宏隔离。
  • 不是"统一封装 MPI"：单节点实现里一个 MPI 调用都没有；多节点实现里 MPI 只是协同手段之一——闸门不走网络（单节点走 host 锁页内存，多节点走共享 device 闩针），分配期的 MPI（fabric 句柄 Bcast）住在 buffer 构造函数里，也不在 NodeHelper。

2.9 doMemcpyCore：把"认领到的活"跑成带宽数字

函数职责（memcpy.cpp L468-646）：接收 dispatch 后的 MemcpyDispatchInfo，执行 averageLoopCount 轮采样（默认 3），每轮内入队并测量 loopCount 次拷贝（默认 16），用 CUDA event 计时，产出每个任务的带宽统计。

  • 5 个 per-task 向量（L469-473）：streams / startEvents / endEvents / bandwidthStats / adjustedCopySizes，按任务数开槽——空闲 rank 长度 0，vector(0) 不分配，一切 per-task 循环自动 0 次。
  • totalEnd 全员都建（L504-505）：空清单 rank 也创建这个 event，为了让代码不用按身份分支。
  • 双重起跑对齐：spin 闸门 kernel 消除 host 入队抖动（GPU 到闸门即停）；cuStreamWaitEvent(startEvents[0]) 链消除任务间相对偏移——所有拷贝从同一时刻起跑。
  • 模板代码零直接 MPI：多节点协同全部通过 nodeHelper——②a/②g 的 Barrier、闸门共享闩针、等流心跳、④ 的结果归集。
  • 空闲 rank = 义务照常：per-task 循环全跳过，但闸门复位/释放、Barrier、totalEnd 创建销毁一步不少（等流循环 0 次——没有自己的流），与执行者保持同节奏。

三、MultinodeDeviceToDeviceBidirTransfer 精读（1 对 1 双向）

3.1 函数功能总结

一句话职责：对每一对 GPU，一次调用内同时开出两个方向相反的拷贝任务（本端→对端 与 对端→本端 并发对开），各自独立计时、独立校验，产出 Write1 / Write2 / Total 三张 worldSize × worldSize 矩阵。

  • 与第二章的关系：引擎层完全复用（pair 生成 → Unicast 构造 → dispatchMemcpy 认领 → doMemcpyCore 采样循环，见 2.4 / 2.5 / 2.7 / 2.9），差异全在用例层：buffer 2 块 → 4 块、任务 1 个 → 2 个交叉任务、出口 FIRST_BW → VECTOR_BW。
  • 谁在跑：4 个 rank 仍跑完全相同的代码；区别是每对出现两个执行者——两端各认领 1 个任务（Write：task0 归 pair.second、task1 归 pair.first），不再是"一人干活三人围观"。
  • 内存从哪来：每对 4 块 Unicast（每端 2 块）。两个方向并发读写，若共用 buffer 会互踩（A 方向的目的地恰是 B 方向的源），必须内存隔离——代价是每端显存占用翻倍（2 × size）。
  • 双向怎么对齐：两端的流各排一个 spin 闸门，由同一块共享 device 闩针（4 字节，物理驻留 rank0 的 GPU、全员映射）一次放行——两级闩针链在双向场景才走满两跳（单向 1 对 1 只有 master 一跳，第二跳无人等待）。
  • 结果怎么归：VECTOR_BW 出口逐任务返回 → calculateVectorBandwidth 按任务表逐个 Bcast → results[0] = task0（对端→本端），results[1] = task1（本端→对端），Total = 两者之和（纯加法，不是 TOTAL_BW 的"总时间"口径）。
  • 镜像复用：pair 循环改走 cachedPairLoop——src > dst 且镜像格 (dst, src) 已有值时三张矩阵直接照抄，不建 buffer、不测量、零 MPI。
  • 每对 MPI 账目（物理测量时）：6 Bcast（4 块 buffer 构造 + 2 次结果归集）+ 14 Barrier（构造 4 + 采样 3 × 2 + 析构 4）；镜像命中的 pair 为零。
  • 用例自述与代码的一处出入：generateDesc 的 CE 变体写"反向拷贝同时运行但不计量"；现行代码两个方向都在 VECTOR_BW 出口独立计量并分别上报（Write1 / Write2 / Total），以代码为准。

五、MultinodeAllFromOneReadSM 精读（1 源多读聚合读）

与第四章互为镜像：每轮锁定一个源 GPU（srcDeviceId），其余 W−1 个 GPU 同时读它——写场景是各执行者"推"数据过 NVLink 到远端目标，读场景是各执行者"拉"远端源数据落到本地。清单组合随之对调：srcNodes 由 W−1 个 Unicast（源，物理显存全在被读方那块卡上）组成，dstNodes 由 W−1 个 Local（读方各自的本地缓冲）组成。偏好为 PREFER_DST，按目标 buffer 的 owner 分活——执行者恰好就是各读方自己，上下文也是读方本地的。出口同为 SUM_BW，含义变成"被读 GPU 的出向聚合带宽"；结果矩阵仍为 1×W，每列对应一轮被读的源卡。

表结构与第四章一致：阶段①为本轮清单构造完成后的状态（过滤前，人人清单相同，差异只在 Local 的"成色"）；阶段②为 dispatchMemcpy 认领后的状态（每个读方认领 1 个任务，被读源认领 0 个）；最后一行为本轮实际动作。
