多节点 D2D「1 对 1」：4 rank 执行顺序与 MPI 流程

节点 A / B 各 2 个 GPU，worldSize = 4，每进程绑定 1 个 GPU。本轮只看一对：A·GPU0（rank0）→ B·GPU0（rank2）。全程只有 rank0 的 GPU 在做拷贝，rank1 / rank3 只出现在 MPI 集合操作上，rank2 只提供 dst 显存。

4. 一个 pair 的完整生命周期

  1. T0 启动，没有全局 Barrier：MPI_Init、MPI_Comm_rank/size、MPI_Allgather 交换 hostname 和 deviceCount，localDevice = localRank % 2；随后各 rank 本地 cudaSetDevice + cudaMalloc(1KB) 健全性检查 + preloadKernels。这一步没有显式 Barrier，因为只需要交换元数据。
  2. T0b 建共享闸门：new NodeHelperMulti() 时 rank0 在 GPU 上 cuMemCreate(4B) 并导出 handle；因为只有 rank0 拥有这块内存，所以是 rank0 单点广播（不是 Allgather），4 个 rank 各自 import/map，最后 MPI_Barrier。这是整轮测试的第一次 device 空间申请。这块 4B 不存测试数据，它是 spin kernel 的放行开关（latch）：4 个 rank 映射的是同一份物理内存，master 往里写 1，各 GPU 上自旋等待的 kernel 看到后立即放行后续拷贝（见 T8）。
  3. T1a 生成 / 广播 pair（循环之前，只一次）：rank0 枚举 12 个有序对、采样、用固定种子 shuffle，然后两次 MPI_Bcast（数量 + 数据）；其他 rank 只接收并反序列化，所以 4 个 rank 的列表和顺序完全一致。
  4. T1b 进入 for 循环：每轮取出一个 pair，例如 (0, 2)，得到 srcDeviceId = 0、peerDeviceId = 2；从这里到 T17 都在循环体内，共重复 12 次。
  5. T2 分配 src：MultinodeDeviceBufferUnicast(size, 0)。rank0 cuMemCreate + export；MPI_Bcast handle；4 个 rank 都 reserve/map/setAccess；MPI_Barrier。
  6. T3 分配 dst：MultinodeDeviceBufferUnicast(size, 2)，owner 换成 rank2，其余流程相同。
  7. T4 dispatch 过滤：每 rank 都算出 ranksUnfiltered = 0（src owner），只有 rank0 满足 == worldRank，保留 1 对；其余为 0 对。
  8. T5–T14 采样 ×3：Barrier → memset → 入队 spin → 预热 4 轮 → 计时 16 轮 → release → 等待流 → Barrier → 校验 → 统计。只有 rank0 有 GPU 动作，其余 rank 在第二个 Barrier 上等待。
  9. T15 取结果：calculateFirstBandwidth() 由 rank0 做 root MPI_Bcast。
  10. T16–T17 销毁：dst、src 各一次 MPI_Barrier + unmap/release/free，然后进入下一个 pair。
分配和销毁都在“每个 pair”这一层，3 次采样复用同一对 buffer；不是每次采样重新申请。

6. 关键点

T0 为什么没有 Barrier：启动阶段各 rank 只需要交换 hostname 和 deviceCount（两次 MPI_Allgather），之后全是本地动作（cudaSetDevice、1KB 健全性分配、preloadKernels）。真正的设备空间申请和第一次全局同步发生在 T0b：NodeHelperMulti 在 rank0 上创建 4 字节共享闸门，MPI_Bcast handle 后由全部 rank 映射，末尾 MPI_Barrier。

为什么只有 rank0 忙：PREFER_SRC_CONTEXT 让 dispatchMemcpy 取 src 的 owner（0），再用 ranksUnfiltered == worldRank 过滤，所以只有 rank0 的待执行列表非空。rank2 只提供 dst 显存，rank1 / rank3 只参与集合操作。

ctxPreference 到底决定什么：回答「这一路拷贝以谁的名义发起、在哪个 GPU 上跑」——写场景用 PREFER_SRC_CONTEXT，拷贝在源 GPU 上下文里执行，测「源端的写出能力」；读场景用 PREFER_DST_CONTEXT，拷贝在目的 GPU 上下文里执行，测「目的端的读入能力」（所以 Read 要把实参对调：让落点那侧的 GPU 亲自从远端拉数据）。dispatchInfo 按作用装 4 样东西：① 「我这台进程要干的活」清单——每路 = 源指针 + 目的指针 + 在哪个 GPU 上下文跑；pair (0,2) 下 rank0 拿到 1 路（源 = 本地 VA、目的 = import 的远端 VA），rank1/2/3 拿到空清单，core 里所有「对每路循环」自动空转——这就是空闲 rank 的机械实现；② 全量拷贝清单（不过滤，供结果对位置）；③ 每路执行者的 rank 编号——用来挑 spin 闸门 master、以及结果聚合时当 Bcast root（谁测的谁广播）；④ 空白工作区——core 后续填每路的流 / 截断后字节数 / 循环次数。对照 bisect（VECTOR_BW）：4 路、执行者 0/1/2/3 各 1 路，谁都不空转，聚合时按执行者逐路 Bcast 拼回完整结果。

空闲 rank 具体在等哪里：它们完整跑完 doMemcpyCore，但本地 buffer 数为 0，memset / kernel / event / 统计全部空转；streamBlockerReset 里的 cuMemsetD32 会写共享闸门（唯一碰 GPU 的动作）。真正的等待点是 T12 的 MPI_Barrier：rank0 完成 16 轮拷贝后才到达。

dispatchMemcpy 逐步走（pair (0,2)、Write）：4 个 rank 都执行这个函数且函数内一行 MPI 都没有——各 rank 的 buffer 对象是同构副本（owner 元数据构造时已烙进），同样规则各自算、结论必然一致，分活不需要通信。第一步「标注」：Write 下执行者 = src 的 owner = 0（4 个 rank 算出同样的 {0}），但记下的 ctx 是本进程自己的 GPU（getPrimaryCtx 永远返回调用者 localDevice 的 ctx：rank0 记 A·GPU0、rank1 记 A·GPU1、rank2 记 B·GPU0、rank3 记 B·GPU1）。第二步「认领」：== worldRank 只有 rank0 保留这一路（源指针 + 目的指针 + A·GPU0 ctx），其余 3 个 rank 得空清单——core 里所有「对每路循环」零次迭代，自动空转。第三步「记 master」：rankOfFirstMemcpy = 0 在全员身上设置（不是只有 rank0），后续 spin 闸门 master 和结果 Bcast root 都靠它，全员记同一个值集合操作才对得上。Read 方向对照：实参对调 + PREFER_DST → 看 dst（= srcNode）的 owner = 0，执行者还是 rank0 但方向相反；N 路场景（bisect 4 路 / AllToOne 3 路）同一套两步走，每个 rank 恰好认领自己那些路。

dispatchMemcpy 代码级细节：① ranksUnfiltered 初始值 -1 是哨兵——没被标注执行者的路在认领循环里 -1 == worldRank 永不成立，自动静默丢弃，无需专门清理；② 标注循环的 else if 不检查 PREFER_DST_CONTEXT，它是兜底分支：PREFER_SRC 是「偏好」不是「强制」，src 侧没有设备上下文（host 类 buffer）时回退到 dst 侧；PREFER_DST 则没有回退到 src 的路径（不对称）。D2D 的设备 buffer ctx 恒非空，此分支从不触发；③ rankOfFirstMemcpy 取自未过滤表的首元素且是 NodeHelperMulti 成员变量——全员记同一个值、跨整个 doMemcpyCore 存活，spin master（streamBlockerBlock）和结果 Bcast root（calculateFirstBandwidth）都从它取；④ 空表守卫（size() > 0）避免 [0] 越界。

MPI 在每个 pair 里的固定开销：2 次 Bcast（src/dst handle）+ 2 次 Barrier（映射完成）+ 6 次 Barrier（3 次采样 × 2）+ 1 次 Bcast（结果）+ 2 次 Barrier（析构）。这就是 1 对 1 用例在 4 rank 下看起来“同步很多”的原因。

为什么不是每个 rank 都 cuMemCreate：unicast buffer 的语义是“一份物理显存 + 多进程映射”。owner 由构造参数 MPI_rank 决定（src buffer 是 srcDeviceId，dst buffer 是 peerDeviceId），所以 if (MPI_rank == worldRank) 只有 owner 成立：只有它 cuMemCreate / export，其余 rank import 同一个 fabric handle 再映射。如果每个 rank 都自己 create，就会得到 4 块不同的显存，拷贝目标就错了。注意只是“每块 buffer 一个 owner”，12 个 pair 跑下来每个 rank 都会轮到当 owner。

src（pair.first）的导出 / 广播确实没有必要——这是代码的统一写法，不是功能需要：本用例里 pair.first 的 buffer 只有它的 owner 自己会碰：Write 方向执行者就是 src owner（读自己的 src、写远端 dst）；Read 方向（同一个类，doMemcpy(peerNode, srcNode) 实参对调 + PREFER_DST_CONTEXT，见 multinode_testcases.cpp L63-66）执行者仍是 rank0，读远端 peerNode、写自己的 buffer。两个方向都只有 pair.second（peerNode）需要跨进程映射。代码库有对应的本地分配类 MultinodeDeviceBufferLocal（owner cuMemAlloc，不 export / 不广播），且在方向固定的用例里正是这么用的：AllToOneWrite 的 3 个 src 全是 Local、只有 dst 是 Unicast；AllFromOneRead 正好反过来。D2D 因为一个 run() 体同时服务 Read / Write 两个方向（唯一区别是实参对调），两边就统一都用了 Unicast——pair.first 的 export + Bcast + import + map 是纯开销（每 pair 一次，全在计时窗口外）。

MPI_Bcast 不是 Barrier：它是集合操作，4 个 rank 都调用同一个函数，root 发送、其余接收；接收方会阻塞到数据到达，所以有“数据对齐”的效果，但它不保证所有 rank 都已到达同一点（root 可能先返回）。因此代码在映射完成后另外调用 MPI_Barrier。T0b 的闸门只有 rank0 拥有，是单点 Bcast，不是 Allgather；每个 rank 拿到的是同一份 handle。

T1a 里那个多出来的 Barrier（generateTestPairs 内部）：该函数被每个 D2D 系用例反复调用（D2D + bidir 各方向变体），内部用函数级 static 缓存 + pairsCalculated 标志实现「只算一次」：第一次调用全员跌落，rank0 生成、MPI_Barrier、所有 rank 置位标志、两次 Bcast、非 root 反序列化填充自己的缓存副本；之后的调用所有 rank 同时满足早退条件、纯本地返回缓存，连 Bcast 都不再发。关键行是「全员置位标志」——若只对 rank0 置位，第二次调用 rank0 早退不进 Bcast、其他 rank 卡在 Bcast 等一个永不到来的 root，直接死锁。Barrier 本身的作用是把标志翻转对齐到「rank0 已生成完毕」之后；单看第一次调用，后面的 Bcast 也会让非 root 等到 root，所以它偏防御式显式对齐。

下一个 pair (1, 3) 的完整角色重分配：没有角色切换代码，一切由当前 pair 的 src rank 数据驱动。回到 T1b 取出 (1, 3)：src = A·GPU1（rank1）、dst = B·GPU1（rank3）。T2 的 owner 换成 rank1（rank1 cuMemCreate + export，MPI_Bcast root = 1，其余 3 个 rank import / map）；T3 的 owner 换成 rank3（root = 3）；T4 算出 ranksUnfiltered = 1，rank1 成为唯一执行者兼 master（rankOfFirstMemcpy = 1）；T7 的 memset、T13 的 memcmp、T15 结果 MPI_Bcast 的 root 全部换成 rank1；上一对的 rank0 / rank2 退化为只在映射和集合操作中出现，在 T12 的 Barrier 上等待。T16 / T17 析构后取第 3 个 pair，依此类推跑完 12 对。逐步时间线见第 8 节。

“同时”不适用于这里：1 对 1 一次只搬运一个 pair；多打一才是 3 个源 rank 并发写同一个目标。

doMemcpyCore 里一行 MPI 都没有：这是设计使然——MPI 全部藏在 nodeHelper 接口后面，core 只调接口：synchronizeProcess() 在 NodeHelperMulti 里是 MPI_Barrier（T6 / T12），streamBlockerReset / Block / Release 是 4B 闸门 + spin kernel（T6 / T8 / T11），streamSynchronizeWrapper 是 cuStreamQuery 轮询 + MPI_Iprobe 保活（T11），calculateFirstBandwidth 等是 MPI_Bcast / Allreduce（T15）。单节点跑 NodeHelperSingle（同步是空操作、blocker 是本地内存），多节点跑 NodeHelperMulti，core 一行不改。

计时口径：只覆盖 T10 那次 kernel 的 16 轮拷贝。T7 的 memset 和 T9 的预热（同一次 kernel 启动、内部 4 轮）都不进计时窗口。SM 打流不是 cudaMemcpy：一次 stridingMemcpyKernel 启动、16 轮在 kernel 内部循环，start / end 事件测的是 GPU 上的真实执行窗口。闸门管「起跑」，不管「终点」——T8 的 spin kernel 挡在流最前面，放行后预热、事件、拷贝在 GPU 侧连续执行，host 入队抖动被挡在窗口外；结束判定靠 cuStreamQuery 轮询 + end event，不靠闸门。

7. 结果如何得到

rank0 用自己流的 start / end 事件算出本对带宽：adjustedCopySize × loopCount / elapsed；adjustedCopySize 会按 SM 线程数向下截断到 16 字节倍数。

3 次采样取统计值后，calculateFirstBandwidth() 以 rank0 为 root 做 MPI_Bcast，4 个 rank 拿到同一个标量；结果写入 PeerValueMatrix 的 (0, 2) 位置。

输出标签为 memcpy SM GPU(row) <- GPU(column) bandwidth (GB/s)，只有 rank0 打印。之后继续下一个 pair，直到 12 对跑完。
